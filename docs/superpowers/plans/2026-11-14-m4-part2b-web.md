# M4 part 2b: the panel changes config Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A person changes the router's config from the panel: the WAN page and the LAN & DHCP page edit one draft, one dialog shows what an apply changes and interrupts, and a banner on every page counts down until the change is confirmed or the router goes back.

**Architecture:** `@openfeo/client` gains the five config calls; an apply or a revert whose answer never comes is a result (`answered: false`), not an error, because a change that moves the router's address takes the answer's way home with it. `@openfeo/ui` gains the form components the design system already styles. The panel gains a shell that every page behind the login sits in, one config store beside the session (the config as read, the draft, their difference, what is pending), pure model functions under `model/` (addresses, field checks, the rule that carries addresses along with a renumbered LAN, the list of changes) and the two pages. The router gains one thing: `effects` says when a change replaces a static WAN's address or port.

**Tech Stack:** as part 1b: Vue 3, TypeScript 6, Vite, vitest with happy-dom, Playwright, protobuf-es; Rust for one task and the harness. No new dependency, in npm or in cargo.

**Spec:** `docs/superpowers/specs/2026-11-11-m4-part2-changing-config-design.md`: "Part 2b: the web", "Proven" from "`@openfeo/client`'s own tests" on, "Calls made for the maintainer", and "After part 2a" (above all "For part 2b"). SPEC §5.5, §8.3, §8.4, §12. The approved mockup is not in the repository; its words are copied into the tasks below and are binding.

**Not in this plan:** any page but these two (part 3); editing a LAN's tagged members, `reaches`, port forwards, rules, DNS records or public blocks; renaming a WAN or a LAN; new config fields; ordering the appliers after the stops, and answering an apply before it is published (both are the maintainer's open questions from part 2a).

## Calls this plan makes beyond the design

Each is the plan's, to be reported with the executor's rulings.

1. **An apply or a revert that is not answered within 10 s is `answered: false`, whatever the validation said.** The client then treats the socket as lost and remakes it. The panel reads the router's config and state when it next reaches it and says what it finds. Cost: a refusal lost on the way reads as "no answer" for a moment, until the config is read again and the draft is found unapplied.
2. **"The same place in the new subnet" means: an address still inside the new subnet stays where it is; one left outside moves to the same distance from the start of the subnet; one with no such place is left as it was and marked.** The design's sentence alone would move a pool from `192.168.1.100` to `192.168.0.100` when a /24 is widened to a /23 around the same router address. Cost: after a move to an overlapping subnet some addresses stay and some move, each saying which.
3. **A draft with changes is kept whole when the config changes under it.** There is no merge: what the other session changed shows in this draft as a change back, in the bar's count and in the dialog, and a notice says the config was changed elsewhere. Cost: someone who applies without reading the dialog undoes the other change.
4. **A change is counted per setting, as the dialog lists it:** one for each setting of a WAN or a LAN that differs, one for a pool (both ends), one for a LAN's reservations together, one for a WAN or LAN added or removed, one for each address elsewhere that a renumbering carried, and one for any other difference, by its path. Cost: "3 changes" is the panel's count; the router counts effects.
5. **The dashboard moves into a shell shared by every page behind the login,** and the router's state, counters and events are listened to once, by the shell. Cost: part 1b's dashboard tests mount the shell.
6. **`effects` reports a static WAN whose address, gateway, port or tag changes as `WAN_RECONNECTS`.** It has no task and so had no slice, and the dialog would have said such a change interrupts nothing. Cost: for a static WAN the word means its address or port is replaced, not that a client is restarted.
7. **The draft is dropped when the session ends, however it ends.** It may hold a typed password. Cost: a draft lost to a session that lapsed.
8. **A tab whose address the change took away says where the router went**, with links to its name and to the new address, since nothing the router sends can reach that tab again.
9. **A setting put back to what the router's config means takes that config's own spelling** (a field absent, or present and empty), so that it counts as no change; a type or a DHCP server switched away from and back to within one draft keeps what was typed for it.
10. **The lease time is a choice of 1 hour, 12 hours, 1 day, 1 week, or Other with the seconds typed; the subnet size a choice of /16 to /30 with the count of addresses,** the current value always among them. Cost: an unusual value is two clicks away.
11. **A WAN's port may be one that is in use elsewhere; the list says where, and the router's refusal is shown at the field.** A LAN's ticks offer only free ports and its own, as the design says.
12. **A new WAN or LAN is named in a small dialog** and the name cannot be changed after. A new WAN starts as DHCP on the first free port with a priority 10 above the highest; a new LAN starts with no address, no ports and no DHCP server. Turning a DHCP server on for the first time proposes the pool from the 100th to the 200th address of a subnet that has them.
13. **The browser run uses a 40 s window** (`openfeo.confirm_secs=40`): long enough to re-home the LAN host and log in again at the new address, short enough to wait out once.

## Review Focus

1. **An apply that is never answered.** The panel must not wait for ever, send the apply twice, or lose the draft, and must find the pending change when it reaches the router again. Pinned by `an apply with no answer within the wait is unanswered, and the socket is remade` (Task 3), `an unanswered apply is settled by what the router then says` (Task 10) and the subnet change in the browser (Task 15).
2. **The config changes under a draft** (another session applies, a revert, a reboot) and the tag goes stale. Pinned by `a draft with changes is kept when the config changes elsewhere, and says so` and `an apply the router refuses reads the config again and keeps the draft` (Task 10).
3. **A typed password escaping the tab's memory.** Pinned by `a typed password is in no storage and not in the list of changes` (Task 10) and `the password field is empty again after an apply` (Task 11).
4. **A renumbering that does not fit:** a smaller subnet, an overlapping one, a rule whose target is a range or a block. Pinned by the cases of Task 8 and `an address with no place in the new subnet is marked at its field` (Task 12).
5. **The countdown when the tab slept, the clocks differ, or the router's clock is not yet set.** It must never go below zero, never read the browser's clock as the router's, and give way to the truth when the state arrives. Pinned by `the countdown is the router's clock, not the browser's` and `a tab that slept past the window shows no negative time` (Task 14).

**How it behaves.**
- It reads the config when it starts, each time the socket opens again, when a `config.*` event comes among the events the shell already listens to (`live.events`), and whenever `pending` appears, goes, or is another one. Reads are one at a time; a read asked for during a read happens once after it. (An event from the backlog costs one read more and changes nothing.)
- A read that brings another tag: a draft with no changes becomes the new config; a draft with changes is kept, `base` and the tag move, and the notice is `changed-elsewhere` (call 3).
- `apply`: sends the draft with the tag. Answered: the draft becomes the base, every PPPoE password in the draft is emptied, and what was sent is remembered with the tag it was edited from while the change is pending. Unanswered: the same is remembered and the config is read as soon as the router is reached. When the review's caller said `connectionDrops`, the notice is `moved` (call 8). A refusal (`FAILED_PRECONDITION`, `INVALID_ARGUMENT`): the notice is `refused` with the router's words, the config is read again, the draft is kept.
- What became of a pending change is settled by the read that follows its going from the state. It was reverted when the tag read is no longer the one read while it was pending, or when `live.events` holds a `config.reverted` event no older than the change's `applied_uptime_ms` (two configs that differ only in a PPPoE password share a tag, so the tag alone cannot say); the notice is then `reverted`, its `why` the event's (`restart` reads as `unknown`), `unknown` with no event. Otherwise it was confirmed and nothing is said.
- The tab that made the change gets its draft back with that notice: the draft becomes what was sent, over the base just read, and `draftKept` is true. The same holds for an unanswered apply that the next read finds neither pending nor in force (the tag is still the one it was edited from). A confirmed change is forgotten. In any other tab `draftKept` is false.
- `readOnly` is `The router refused its config file and runs on defaults. Mend or remove the file to change settings here.` while the state has a `configProblem`; `edit` then does nothing.
- The session ending (`router.onSessionEnd`) drops the draft, the notice and what was remembered (call 7).
- While the draft has changes the store holds a `beforeunload` listener that asks before the page is left; with none it holds no listener.
