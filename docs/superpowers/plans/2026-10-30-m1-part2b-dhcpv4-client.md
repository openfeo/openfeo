# OpenFeO M1 part 2b — WAN DHCPv4 Client Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A WAN configured `[wans.dhcp]` obtains its address, gateway, routes, MTU and DNS from the ISP's DHCPv4 server through an in-house sans-IO client, keeps the lease renewed, survives a link flap and a reboot with the same address, and the lab proves it against Kea: NAT works on the leased address, renewal happens at T1, a link flap re-acquires, a reset reuses the lease through INIT-REBOOT, and a missing server never stops the LAN.

**Architecture:** `openfeo-proto-dhcp4` is pure: the DHCPv4 wire format (header, options, RFC 3396 long options, option overload), the IPv4/UDP encapsulation the raw-socket path needs, RFC 4361 identifiers, and the client state machine `Client::handle(Input, now) -> Vec<Output>` (SPEC §6.3). `openfeo-net` owns the sockets and timers: an AF_PACKET socket bound to the WAN port while the client has no address, a UDP socket with `SO_BINDTODEVICE` once bound (SPEC §7.2). The router runs one supervised task per DHCP WAN that feeds link facts in and publishes the lease as a World fact; `reconcile::routing` and `reconcile::links` turn the fact into the address, routes and MTU; the lease is persisted under `/state/leases` and the DUID under `/state/identity` (SPEC §5.2). `dhcproto` is a dev-dependency only: a differential oracle for our codec in unit tests and a fuzz target; it ships nowhere.

**Tech Stack:** Rust 1.99 edition 2024; nix 0.30 (`net` feature) for AF_PACKET and socket options; tokio (`AsyncFd`, `UdpSocket`, timers); dhcproto 0.15 as dev-dependency and fuzz dependency; libfuzzer-sys via cargo-fuzz; Kea 2.4+ in the lab (3.2 locally, Ubuntu's in CI) with short lifetimes; the existing rootless sandbox and QEMU harness.

**Spec:** `SPEC.md` — §2 (Memory-safe parsers, Async runtime), §5.2 (`identity/`, `leases/`, durable writes), §6.2 (fact sources, World), §6.3 (sans-IO cores, drivers in `openfeo-net`), §7.2 (DHCPv4 client), §7.4 (routes tagged 200), §8.2 (`[wans.dhcp]`), §9 (memory safety; ADR-0013 for the one unsafe module), §11 (fuzz targets), §12 row M1, §13 (crates `openfeo-proto-dhcp4`, `openfeo-net`; dependency rules). RFC 2131, RFC 2132, RFC 3396, RFC 3442, RFC 4361.

## Global Constraints

- Everything in the M1 part 1 and part 2a plans' Global Constraints still holds (identity `andy@vitri.ltd`, commits `-s` with both trailers, lints, SPDX headers, no `unwrap`/`expect` outside tests, pure crates, `std::process::Command` only in `harness/` and `image/`, every parser gets a fuzz target in the PR that adds it, the repository is public).
- `openfeo-proto-dhcp4` is pure (SPEC §13): no `tokio`, `libc`, `nix`, `socket2`, sockets or clocks anywhere in its normal dependency tree. `dhcproto` appears only under `[dev-dependencies]` and in `fuzz/Cargo.toml`; `scripts/check-deps.sh` reads `cargo tree -e normal`, so the rule still holds and `make lint` proves it.
- `unsafe` is allowed in `openfeo-net` only inside `src/sys.rs`, every block with a `// SAFETY:` comment (ADR-0013 in Task 4 amends SPEC §9 and CLAUDE.md, which today name only `openfeo-init` and `openfeo-nft`). Everything else in the crate is under `#![deny(unsafe_code)]`.
- SPEC §7.2 verbatim: AF_PACKET in INIT/SELECTING, UDP with `SO_BINDTODEVICE` once bound; persisted client-id (`identity/`); INIT-REBOOT with the last lease after a reboot; options requested: subnet mask, router, DNS, domain name, broadcast, MTU, classless static routes (121, plus 249 for compatibility), NTP, renewal and rebind times; honours T1/T2 and lease expiry; publishes address, gateway, DNS servers, static routes and MTU as facts; vendor class and hostname options configurable.
- Identifiers (my call, from SPEC §5.2's "DUID, IAIDs, DHCPv4 client-id"): DUID-LL (type 3, hardware type 1) from the MAC of the lowest-numbered port with a MAC, generated once and kept as lowercase hex in `/state/identity/duid`; IAID = the last four bytes of the WAN port's MAC; client identifier = `0xff` + IAID + DUID (RFC 4361). `chaddr` is the port's MAC.
- Durable writes are `openfeo_platform::atomic::write` with mode 0600 (SPEC §5.2). The lease file is written on every bound and renewed lease (a few per hour); the DUID once.
- Routes from a lease carry `RTPROT_OPENFEO` and the WAN's priority as metric in the main table, like the static WAN's (SPEC §7.4). When option 121 (or 249) is present, option 3 is ignored and a `0.0.0.0/0` classless route is the default route (RFC 3442 §Requirements). Lease MTU outside `576..=9216` is ignored with a warning.
- Timers: T1 and T2 default to 0.5 and 0.875 of the lease when absent or inconsistent (T1 ≥ T2 or T2 ≥ lease); a lease of `0xffffffff` never renews or expires. Retransmission of DISCOVER and REQUEST: 4, 8, 16, 32, 64 s with ±1 s jitter, then 64 s forever in SELECTING; REQUESTING and REBOOTING give up after 3 sends and return to INIT (REBOOTING withdraws the lease). RENEWING and REBINDING retransmit at half the time remaining to T2 / expiry, never less than 60 s (RFC 2131 §4.4.5). The BROADCAST flag is set on every message sent while the client has no address.
- Console lines are a contract with the scenarios (exact text, `{}` are values): `identity: duid {hex} ({new|known})`; `wan {name} dhcp discover`; `wan {name} dhcp offer {addr} from {server}`; `wan {name} dhcp request {addr}`; `wan {name} dhcp bound {addr}/{prefix} via {gateway|none} lease={n}s t1={n}s t2={n}s server={server}`; `wan {name} dhcp options dns={a,b|none} domain={d|none} mtu={n|none} routes={count}`; `wan {name} dhcp renewed {addr}/{prefix} lease={n}s`; `wan {name} dhcp init-reboot {addr}`; `wan {name} dhcp nak {message|-}`; `wan {name} dhcp expired`; `wan {name} dhcp reboot timed out`; links applier `set {port} mtu {n}`.
- Kea in the lab serves `203.0.113.100-200` with valid 60 s, renew 20 s, rebind 40 s and the options routers, DNS, domain `isp.example`, MTU 1400, NTP, and classless routes `0.0.0.0/0 - 203.0.113.1, 198.51.100.0/24 - 203.0.113.1` (Task 4 changes the one template; M0's start scenario and `make run` use it too). Because 121 is present the client ignores option 3 and the default route comes from the classless list, as RFC 3442 intends.
- `via` in the `bound` line is `Lease::default_gateway()`: the gateway of a `0.0.0.0/0` classless route when routes are present, else option 3's first router, else `none`.

## Review Focus

1. No DHCP server answers at boot (ISP down): the LAN is served, `ready` is announced, discovery retries with backoff forever and nothing is forwarded to a WAN without a route. Tests: Task 2 `discover_retransmits_with_backoff_capped_at_64s`; Task 8 scenario `dhcp_without_a_server_keeps_the_lan_working`.
2. The box moves to another ISP and reboots with a stale lease: INIT-REBOOT is NAKed, the stale address is never configured and discovery starts. Test: Task 3 `nak_while_rebooting_withdraws_the_lease_and_discovers`.
3. Hostile or broken replies (another client's xid or chaddr, truncated options, missing cookie, a 121 option with impossible lengths): ignored, never a panic, never a bound lease. Tests: Task 1 `truncated_and_malformed_inputs_are_errors_not_panics`, `classless_route_with_impossible_length_is_rejected`; Task 3 `replies_for_another_client_are_ignored`; fuzz targets `dhcp4_message`, `dhcp4_differential`.
4. Absurd lease values (MTU 100, T1 after T2, lease 0): sane defaults, nothing applied blindly. Tests: Task 2 `timers_default_when_missing_or_inconsistent`; Task 3 `mtu_outside_sane_range_is_dropped`, `ack_without_lease_time_or_server_id_is_ignored`.
5. A lease with classless routes but no usable default (routes only to prefixes): installed as given, no default route invented, option 3 ignored per RFC 3442. Test: Task 6 `classless_routes_replace_the_router_option`.
